# Data Security Audit — «Медикаменте» (As-Is)

## 1. Цель аудита

Провести анализ текущих процессов компании, сопоставить их с архитектурными практиками и требованиями безопасности, выявить проблемные зоны в обращении с конфиденциальными данными.

---

## 2. Обнаруженные типы данных

| Категория данных          | Примеры                                  | Уровень чувствительности |
| ------------------------- | ---------------------------------------- | ------------------------ |
| Персональные данные (PII) | ФИО, дата рождения, телефон, email       | PII                      |
| Медицинские данные (SPII) | Диагнозы, жалобы, анализы, назначения    | SPII                     |
| Финансовые данные         | Данные об оплате, чеки, суммы транзакций | Финансовые               |
| Контрактные данные        | Условия обслуживания, договоры           | PII                      |

---

## 3. Проблемные зоны безопасности (As-Is)

| №   | Проблемная зона                                            | Описание                                                                                        |
| --- | ---------------------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| 1   | Открытое хранение чувствительных данных                    | Excel, JPG, PDF-файлы на общем диске без шифрования или разграничения доступа                   |
| 2   | Отсутствие разграничения доступа (RBAC / ABAC отсутствует) | Все сотрудники могут иметь доступ к чужим данным                                                |
| 3   | Отсутствие аудита доступа и логирования действий           | Невозможно отследить, кто и когда получил доступ к конфиденциальным данным                      |
| 4   | Отсутствие шифрования данных при хранении и передаче       | Нет защиты данных at rest и in transit                                                          |
| 5   | Ручной ввод и дублирование данных                          | Повторный ввод в Excel и 1С без валидации, высокий риск ошибок и расхождений                    |
| 6   | Несогласованное хранение данных в нескольких местах        | Отсутствует единый источник правды (SSOT), данные хранятся в Excel, 1С, на диске                |
| 7   | Устаревшая архитектура (1С в файловом режиме)              | Нет централизованного контроля, нет возможности аудита или масштабирования                      |
| 8   | Избыточный сбор данных                                     | Собираются лишние данные, которые не требуются для оказания услуг (нарушение Data Minimization) |
| 9   | Отсутствие контроля взаимодействий между системами         | Нет сегментации сетей и маршрутов для потоков данных между Excel, 1С и почтой                   |
| 10  | Отсутствие мониторинга подозрительной активности           | Нет автоматического обнаружения инцидентов безопасности                                         |

---

## 4. Сопоставление с архитектурными практиками

| Принцип безопасности                    | Состояние в компании (As-Is)                   | Соответствие |
| --------------------------------------- | ---------------------------------------------- | ------------ |
| Privacy by Design                       | Не реализован, данные не защищены по умолчанию | ❌           |
| Data Minimization                       | Не соблюдается, данные собираются избыточно    | ❌           |
| Data Lineage                            | Нет отслеживания происхождения и потока данных | ❌           |
| Role/Attribute-based Access (RBAC/ABAC) | Не применяется                                 | ❌           |
| Аудит и логирование                     | Не реализовано                                 | ❌           |
| Шифрование данных                       | Отсутствует полностью                          | ❌           |

---

## 5. Вывод

Текущие процессы компании «Медикаменте» не соответствуют базовым требованиям по безопасности персональных и медицинских данных. Архитектура систем хранения и обработки данных не предусматривает ни разграничения прав, ни защиты, ни аудита доступа, что создаёт высокие риски утечек, нарушений 152-ФЗ и потери клиентского доверия.

Дальнейшие шаги: проработка целевого состояния (To-Be), реализация механизма тегирования, внедрение RBAC, журналирования, шифрования и безопасных интеграций.
